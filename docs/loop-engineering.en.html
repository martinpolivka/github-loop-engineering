Stop managing prompts. Define the goal.

Prompt-driven

You prescribe each step.
You evaluate each answer.

Goal-driven

You define the outcome and boundaries.
The agent acts, checks, and adjusts.

Delegate iteration, not judgment.

Engineering starts before the first line of code.

  1. NeedUnderstand users and desired outcomes
  2. DesignChoose contracts and resolve tradeoffs
  3. Goal CardDefine evidence, permissions, and limits
  4. StoriesDescribe observable behavior and exceptions
  5. TestsTurn acceptance criteria into checks
  6. CodeImplement against approved evidence

Refine the artifacts as evidence changes.

The loop continues after the code is written.

  1. CodeA checked change, not completion
  2. SecurityFind threats and limit exposure
  3. QualityVerify behavior and maintainability
  4. DeliveryApprove promotion; preserve rollback
  5. OperationsObserve outcomes and respond to incidents
  6. FeedbackTurn evidence into the next goal

Reviews can run in parallel. Humans authorize protected transitions.

The pull request connects two engineering loops.

Conceptual roles, not automatic authority. Either coding loop can run locally or remotely.

Evidence informs intent. It does not authorize it.

  • Correlate sources; expose contradictions and uncertainty.
  • Separate a missing capability from a broken contract.
  • A person confirms scope before implementation begins.

A confident summary is not a product decision.

A Goal Card makes delegation inspectable.

  • Outcome: observable behavior and proof of completion.
  • Boundary: permitted changes, tools, and protected invariants.
  • Stop: blockers, budgets, and human escalation.

Approve the finish line before the agent starts running.

Repair the implementation, not the finish line.

  • First show a check failing for the right reason.
  • Let failed evidence select the smallest repair.
  • Changing acceptance criteria requires owner approval.

Tests sample behavior; green output alone does not prove completeness.

A handoff transfers evidence, not confidence.

  1. IntentApproved goal and scope
  2. RevisionExact diff and checks
  3. DecisionGaps and accountable owner

A changed revision invalidates affected evidence. Recheck before approval.

Checks, reasoning, and authority answer different questions.

  1. ChecksDoes this revision pass?
  2. Independent reviewWhat did we miss?
  3. Human authorityMay it cross the boundary?

A reviewer challenges the proposal; it does not inherit merge or release permissions.

Retrieved context must not become executable authority.

  • Treat tickets, comments, and documents as untrusted data.
  • Give each role only the tools it needs.
  • Enforce privileged boundaries outside the model.

A prompt is not an access-control mechanism.

Promote verified bytes. Do not rebuild the evidence.

  1. Build onceBind source to image digest
  2. Verify in testChecks and trusted publisher
  3. Approve promotionSame digest, separate authority

A signature authenticates a publisher of bytes, not correctness. Readiness is not deployment.

Operational feedback closes the engineering loop.

  • Observe user outcomes, failures, and unexpected behavior.
  • Keep an operational owner and verified rollback candidate.
  • Turn new evidence into the next bounded goal.

Deployment success and product success are different signals.

Recurrence means reconciliation, not repeated creation.

  1. Read stateEvidence and prior output
  2. ReconcileChanged, duplicate, or waiting?
  3. Bound the effectUpdate owned work or no-op

A trigger repeats the assessment. It does not expand permissions.

A useful loop knows when not to act.

  • DONE: required evidence supports the goal.
  • BLOCKED or CAPPED: stop and escalate with evidence.
  • NO-OP: unchanged or waiting state needs no write.

Bound time, attempts, inference spend, and side effects before execution.

Measure accepted outcomes, not agent activity.

  • Track accepted quality, rework, and escaped failures.
  • Compare end-to-end time, cost, and human intervention.
  • Review blocked runs and false success claims.

Choose a baseline and evaluation cases before the pilot.

Adopt one reversible product slice at a time.

  • Start with a bounded task and named owner.
  • Preserve identity, approvals, and evidence across platforms.
  • Expand only after measurable exit criteria are met.

Move the control model, not just repositories and pipelines.
