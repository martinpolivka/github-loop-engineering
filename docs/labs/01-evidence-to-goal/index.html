Correlate evidence

Start from signals,
not a solution prompt.

  • The agent connects scattered evidence.
  • Citations make claims inspectable.
  • A person confirms scope.

context/intake/ contains synthetic snapshots of a support case, request log, Teams-style discussion, meeting decisions, Outlook-style authorization, and backlog. Approved connectors can retrieve authorized business context in a real environment; the lab uses repository files so every attendee sees the same safe evidence.

  1. Read the files under context/intake/. Separate direct evidence, product decisions, authorization, and unrelated backlog work. Keep SUP-4102/REQ-S12-4102 distinct from SUP-4113/REQ-S07-4113.
  2. Start the coach in one supported surface:
    • Copilot Chat: open Chat in agent mode and name /requirement-refiner in the prompt.
    • Copilot CLI: run copilot, enter /skills list, verify that requirement-refiner is enabled, then name /requirement-refiner in the prompt.
    • VS Code or Copilot app: open the cloned folder and name /requirement-refiner in the prompt.
    • Copilot CLI: run copilot, use /skills list to verify the project skill, then invoke it with its slash-qualified name.
    • An approved agent without Agent Skills discovery can read .agents/skills/requirement-refiner/SKILL.md and follow it exactly.
    1. Open https://YOUR-GITHUB-HOST/copilot, stay in Chat, and select TARGET-OWNER/github-loop-engineering-NN as the repository.
    2. Name /requirement-refiner in the prompt. Repository skills are loaded from .agents/skills/.
    3. Do not start the asynchronous coding agent: this step is an interactive evidence interview and must not create a pull request.
  3. Send: 
    Use /requirement-refiner to analyze the complete synthetic intake packet. Separate every supported case, return a cited evidence brief for each, identify contradictions and unrelated backlog work, and recommend the correct Issue type for each case. Do not create an Issue.
  4. Verify that the feature case describes missing API capability while the bug case proves that the UI hides an existing available value. A different form does not make a request a bug; it must violate a confirmed current contract.
  5. Correct unsupported claims, then send CONFIRMED:.

Expected result: one feature-request draft and one bug-report draft, each with its own citations, scope, acceptance boundary, and risk. No code changed.

Each durable write
needs its own approval.

  • Confirm the exact target repository.
  • Approve feature and bug separately.
  • Keep implementation closed.

The repository already contains two Issue forms under .github/ISSUE_TEMPLATE/: reservation-feature.yml and reservation-bug.yml. You can inspect them in the Code tab; GitHub renders them as choices under New issue. The skill selects the matching form and drafts its fields before any write.

  1. Review both complete drafts and the target resolved by the skill. The feature uses reservation-feature.yml; the bug uses reservation-bug.yml. Compare with the feature reference or bug reference only if you need recovery.
  2. The target must be TARGET-OWNER/github-loop-engineering-NN, must be a fork, and must not equal its parent. In GitHub terminology, the repository owner is the selected organization login in Station or your account login in Sandbox.
  3. Approve the feature draft with the exact repository-qualified line supplied by the agent: 
    APPROVED FEATURE: Create one issue in TARGET-OWNER/github-loop-engineering-NN
  4. Open the returned URL and verify its form, evidence, and fork. Then separately approve the bug: 
    APPROVED BUG: Create one issue in TARGET-OWNER/github-loop-engineering-NN
  5. Open both URLs. Confirm that neither Issue contains implementation guesses and that approval for one did not authorize creation of the other.

You turned one evidence packet into two independently approved work items: a new capability and a reproducible contract violation. Both are now traceable to sources without mixing their scope.
