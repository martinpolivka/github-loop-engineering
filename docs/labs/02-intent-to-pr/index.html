Chapter 2 · 50 minutes · Your own repository, Codespaces and GitHub Copilot

From intent to a verified handoff

Agents write code quickly. The hard part is knowing what to build and proving it works. In this lab you turn noisy team signals into a confirmed requirement, prove the gap with a failing test, let Copilot implement it, and merge only when the check is green and you have reviewed the change.

Result: your own repository with a closed issue, a merged pull request, a red-then-green check history, and a Copilot commit you reviewed.

Set up

Several tools, one loop.

  • Your fork holds the work.
  • Copilot helps you think and build.
  • Checks and review decide.

Fork
Your own copy of a repository that stays linked to the original. About forks.
GitHub Codespaces
A development environment in the cloud: VS Code in your browser, configured by the repository’s .devcontainer/. What are codespaces.
GitHub Copilot
AI assistance in your editor, terminal, and on GitHub, from chat answers to agents that change code. About GitHub Copilot.
Copilot CLI
Copilot as an agent in your terminal, started with copilot. About Copilot CLI.
Custom agent
A file in .github/agents/ that gives Copilot a role, rules, and tools. The coach you use in Step 3 is one. About custom agents.
Copilot cloud agent
Copilot working in the background on GitHub. You ask it with @copilot on a pull request, and it pushes commits for you to review. About Copilot cloud agent.
Issues and pull requests
An issue records what to build; a pull request proposes a change and holds its review. About issues, About pull requests.
GitHub Actions
Automation that runs your tests on every push and shows the result as a check. Understand GitHub Actions.

Your own copy of the service.

  • Fork the workshop repository.
  • Name it with your attendee number.
  • Every later lab uses it.

  1. Open the github-loop-engineering repository in the workshop organization. The facilitator shares the link.
  2. Select Fork.
  3. Set Owner to the workshop organization and Repository name to github-loop-engineering- followed by your two-digit attendee number, for example github-loop-engineering-07. Keep Copy the main branch only selected, then select Create fork.
  4. In your fork, open Actions and select I understand my workflows, go ahead and enable them.
  5. Open Settings, and under Features select Issues.

Expected result: your fork shows forked from …/github-loop-engineering, a pharmacy service in src/, and the Issues and Actions tabs.

Warning

All your issues and pull requests belong in your fork. Whenever GitHub offers a base repository, choose github-loop-engineering-NN, not the workshop repository.

A ready workspace in the browser.

  • Codespaces installs Node and Copilot.
  • Tests run on first start.
  • A laptop clone works too.

Choose one. Codespace is the default because it needs no installation.

  1. In your fork, select Code, the Codespaces tab, then Create codespace on main.
  2. When VS Code asks whether you trust the repository, select Trust Folder & Continue.
  3. Wait until VS Code opens in the browser.
  4. In the terminal, run: 
    gh repo set-default "$GITHUB_REPOSITORY"
  5. Set up the chat panel on the right. If it is closed, select the chat icon at the top of the window.
    • Keep the session type on Local. The same list can also offer other agents, such as Claude.
    • Select Models and sign in. If your account lives on GHE.com, choose Continue with GHE.com and enter your host.
    • Keep the model on Auto.
    • Select Default permissions, then Allow all. This is acceptable only in this disposable Codespace, which holds synthetic data.
  6. Send Hello to test the chat.

You need Git, Node.js 22 or newer, and GitHub CLI signed in to your GitHub host. Choose one agent interface: VS Code with GitHub Copilot, GitHub Copilot CLI, or the GitHub Copilot app.

  1. Clone your fork and run the tests. Replace OWNER and NN: 
    gh repo clone OWNER/github-loop-engineering-NN
cd github-loop-engineering-NN
gh repo set-default OWNER/github-loop-engineering-NN
npm test
  2. Open the folder in your editor or coding agent.

Expected result: npm test ends with ℹ fail 0 and gh repo set-default --view prints your fork.

Why gh repo set-default: your fork’s parent is the workshop repository. Without a default, gh asks which of the two to use, and choosing the parent would open your pull request there.

Decide what to build

Signals are not requirements.

  • The evidence is noisy on purpose.
  • The coach asks; you decide.
  • Nothing is drafted before you confirm.

  1. In your fork, read the four files in context/intake/: the chat thread, the ticket digest, the stakeholder email, and the backlog. Spend two minutes.
  2. Start the coach in the place you prefer:
    • Copilot Chat: open the agent picker and select requirement-refiner.
    • Copilot CLI: run copilot in the terminal, sign in once with /login, enter /agent, and select requirement-refiner.
    • VS Code with Copilot Chat: open the agent picker and select requirement-refiner.
    • Copilot CLI: run copilot in the repository folder, enter /agent, and select requirement-refiner.
    • GitHub Copilot app: open the repository folder and select requirement-refiner from the agent picker.
    1. Open your fork on GitHub. In the upper-right corner, select the Copilot icon, then Chat in immersive mode.
    2. The adjacent Agents icon starts an asynchronous coding task that normally ends with a pull request. Stay in Chat for this coaching conversation.
    3. The coach definition is stored in .github/agents/requirement-refiner.agent.md. Start the chat with: 
      Read .github/agents/requirement-refiner.agent.md and coach me by following it exactly.
  3. Tell the coach, in one sentence, what problem you think the evidence shows. For example: 
    Coach me. I think the evidence points to: customers leave when the kiosk says a medicine is out of stock, even though a similar one is on the shelf.
    Your sentence can differ. The coach questions it either way.
  4. Answer its questions in your own words.
  5. When your need is specific enough to test, send: 
    CONFIRMED: <your final need statement>

Expected result: the coach asks one or two questions at a time and does not give you the answer. After CONFIRMED: it returns an issue draft and marks anything you did not confirm as NOT CONFIRMED. It changes no files.

The issue is the contract.

  • Compare your draft with the product owner.
  • Acceptance criteria stay observable.

  1. Open the product owner's confirmed requirement, feature-request.md, and compare it with your draft. Note one thing you missed.
  2. In your fork on GitHub, select Issues, New issue, then Reservation capability.
  3. Use this title: 
    [Reservation] Suggest an available substitute when stock is zero
  4. Fill in Outcome, Acceptance criteria, Constraints and Change risk from feature-request.md.
  5. Select Create and note the issue number.

Expected result: an open issue, usually #1, that states the observable behavior and limits the change to src/inventory.mjs.

Prove and build

Prove the gap first.

  • Add the acceptance test.
  • Watch it fail locally and in Actions.

  1. In the Codespace terminal, create a branch: 
    git switch -c lab-02-substitute-suggestion
  2. Create test/suggestion.test.mjs and paste the full contents of suggestion.test.mjs.
  3. Run the tests: 
    npm test
  4. Commit, push and open a draft pull request. Replace 1 with your issue number: 
    git add test/suggestion.test.mjs
git commit -m "Add substitute suggestion acceptance test"
git push -u origin lab-02-substitute-suggestion
gh pr create --draft --title "Suggest an available substitute when stock is zero" --body "Closes #1"
  5. Open the pull request link that gh prints, then open its Checks tab.

Expected result: locally, ℹ fail 2: the two tests that expect a suggestion fail. On the pull request, the Test service check turns red for the same reason.

Delegate a bounded change.

  • Mention Copilot on the pull request.
  • Name the only file it may change.
  • The red test is the goal.

  1. On the pull request Conversation tab, add this comment. Replace 1 with your issue number: 
    @copilot Implement issue #1 so the failing tests in this pull request pass.
Change only src/inventory.mjs. Do not edit tests, workflows, package files or server code.
Return one suggestion with sku, name and available: the first same-category product,
ordered by SKU, whose stock covers the requested quantity. Omit it when none qualifies.
Never change stock when you return a suggestion.
  2. Wait for Copilot to react and start a session. Select View session to watch it work.
  3. When Copilot pushes its commit, open Checks. If GitHub shows Approve and run workflows, select it.

Expected result: after a few minutes, a Copilot commit on your branch and a green Test service check.

If Copilot does not respond

Copilot cloud agent needs a plan and policy that allow it. Without it, implement in the Codespace instead: in Copilot Chat switch to Agent mode, paste the same prompt without @copilot, review the change, then run npm test, commit and push. Add Implemented in the Codespace; cloud agent unavailable. to the pull request description.

Review and merge

Review code, not confidence.

  • Two files changed, no more.
  • Green check is required evidence.
  • You merge; the agent does not.

  1. Open Files changed. Confirm that only src/inventory.mjs and test/suggestion.test.mjs changed.
  2. Read every changed line in src/inventory.mjs and answer:
    • Are candidates limited to the same category and sorted by SKU?
    • Does a suggestion leave stock unchanged?
    • Do unknown SKUs still return 404?
  3. Confirm that Test service is green.
  4. Select Ready for review, then Squash and merge.
  5. In the Codespace terminal, run the merged service: 
    git switch main
git pull
npm start
  6. Open the forwarded port 3000, request one MED-003, and select Request reservation.

Expected result: the pull request is merged, the issue is closed, and the service answers 409 with a suggestion of MED-004 while its stock stays at 6.

If you get stuck

Recover without faking evidence.

  • Fix the symptom you see.
  • Label every fallback.
  • Never merge red.

Fork is unavailable
Forking is disabled for the organization or repository. Tell the facilitator.
The workshop organization is not offered as Owner
Tell the facilitator. A fork in your personal account may not support Codespaces or Copilot cloud agent.
Issues or Actions tab is missing in your fork
Repeat Step 1 items 4 and 5 in your fork, not in the workshop repository.
The pull request opened in the workshop repository
Close it. Run gh repo set-default "$GITHUB_REPOSITORY" and create it again, or choose your fork as base repository in the browser.
requirement-refiner is not in the agent picker
Run Developer: Reload Window from the command palette and check that .github/agents/ exists in your repository.
No Copilot is available to you
Pair with a partner who asks you the coach's questions: who has the problem, what they should see when it is solved, what is already in backlog.md, and how a test would prove it.
gh pr create fails
Open your fork in the browser, select Compare & pull request, set base repository to your fork, and create a draft pull request with Closes #1 in the description.
The local run fails for another reason
Compare test/suggestion.test.mjs with the artifact. Only the two suggestion tests may fail.
Copilot changed other files
Comment @copilot Revert every change outside src/inventory.mjs. Do not merge until only the two files remain.
You run out of time
Copy inventory.reference.mjs over src/inventory.mjs, commit it with the message Apply reference implementation, push, and continue with Step 7.

The handoff is not an agent's promise. It is a chain of GitHub records: a confirmed issue, a failing test, a bounded Copilot commit, a green check, your review, and a merged revision that later labs build on.

Make the work provable.
Then hand it off.
