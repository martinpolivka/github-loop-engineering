Approve the Goal Cards

The Issue states the need.
The Goal Card fixes done.

  • Design checks before coding.
  • Approve each finish line.
  • Publish before delegation.

The goal-card skill defines the outcome and finish line; it does not execute the task. Create each card before choosing its coding surface. The executor may repair allowed outputs but may not weaken the card to make its work pass.

  1. Ask the agent to create the feature Goal Card: 
    /goal-card Turn Issue #FEATURE_NUMBER into a ready Goal Card at specs/stock-substitution.goal-card.md. Do not implement it yet.
  2. Answer focused questions only when a missing decision changes the outcome, checks, authority, or limits. Review C01-C03 and compare with the reference feature card only if you need recovery.
  3. Create the bug Goal Card: 
    /goal-card Turn Issue #BUG_NUMBER into a ready Goal Card at specs/partial-stock-visibility.goal-card.md. Do not implement it yet.
  4. Verify that the bug card preserves the API and stock while changing only the visible HTTP 409 result. Use the reference bug card only to recover.

Expected result: both Goal Card files have observable checks, bounded writes, repair paths, approval ownership, and terminal states. Neither implementation has started.

Cloud delegation captures
context at assignment.

  • Publish the complete approved card.
  • Assign only after the comment exists.
  • Keep later steering on the PR.

Copilot cloud agent receives the Issue title, body, and comments that already exist when the Issue is assigned. It does not receive later Issue comments. Let your current agent use GitHub MCP to publish each complete reviewed card, not a link to an uncommitted local file.

  1. Review both local files, then send: 
    Resolve this workspace's exact nameWithOwner, verify it is my fork rather than its parent, then use GitHub MCP to publish the complete reviewed Goal Cards as new comments on OWNER/REPOSITORY#FEATURE_NUMBER and OWNER/REPOSITORY#BUG_NUMBER.

Prefix each comment with "## APPROVED GOAL CARD". Show the exact repository-qualified Issue target and complete comment body, and ask for separate approval before each GitHub write. Do not edit either Issue, assign anyone, or start implementation. After each write, read the comment back and verify that the complete Goal Card is present.
  2. Approve each proposed write only after checking the repository-qualified target, Issue number, and complete comment. Two writes require two approvals.
  3. Open both Issues and compare the read-back comments with the local files. From this point, revise a published Goal Card only through another explicit owner-approved write.
  4. After both read-backs pass, ask the agent to remove the local specs/partial-stock-visibility.goal-card.md. The cloud agent will recreate that card from the bug Issue; keeping it out of the local workspace prevents the feature branch from carrying the unrelated bug Goal Card.

Expected result: GitHub shows two agent-authored, human-approved Goal Card comments, and the agent has verified both persisted writes through GitHub MCP.

Assignment boundary

Assign the bug only after its approved comment is visible. Follow-up information after assignment belongs on the resulting PR with @copilot, where it becomes part of the implementation conversation.

Delegate the bounded bug

Assignment turns an Issue
into asynchronous work.

  • The bug is small and explicit.
  • Copilot owns branch mechanics.
  • The output is always a PR.

  1. Open the bug Issue on GitHub. Under Assignees, select Copilot. Assigning an Issue starts a cloud-agent session and always creates a pull request.
  2. In Optional prompt, enter: 
    Treat the APPROVED GOAL CARD in this Issue as the immutable definition of done. Add it to specs/partial-stock-visibility.goal-card.md, execute its checks and stop conditions, and create the pull request with revision-bound evidence.
  3. Confirm the target repository is your fork and the base branch is main. Start the assignment, then leave it running while you execute the feature locally.

Expected result: the Issue shows an active Copilot session. You do not wait for it; asynchronous delegation creates time for the second loop.

Run the visible inner loop

Work beside the agent.
Choose from failed checks.

  • Branch creation is part of the task.
  • The first check proves the gap.
  • Evidence selects each repair.

Use any approved local agent surface in the repository. At this point the only uncommitted Goal Card in the workspace is specs/stock-substitution.goal-card.md. The instruction owns branch mechanics and makes that card the DoD; it does not require a particular IDE button or Git command.

  1. Send: 
    Create and use a feature branch for Issue #FEATURE_NUMBER.

Treat the APPROVED GOAL CARD in the Issue and specs/stock-substitution.goal-card.md as the immutable definition of done. Execute its assess-act-check-adjust loop.

First establish the acceptance check and show its initial failure before changing production code. Work only within the card's permissions and stop conditions. Stop before committing and present the diff, check results, remaining gaps, and any requested repair.
  2. Inspect the first failed check. It must fail because suggestion is absent, not because of syntax, imports, or weakened existing assertions.
  3. Authorize only the smallest action justified by that failure. Require the agent to rerun invalidated checks after each repair and reconcile C01-C03 against the final diff.
  4. Require the complete deterministic suite before DONE: 
    npm test
  5. When the evidence supports DONE, ask the agent to commit, push, and open a PR against your fork's main. Require the PR body to link the feature Issue, name the Goal Card, and list the checks run.

Expected result: a feature PR contains the approved Goal Card, focused red-then-green evidence, the smallest permitted implementation, and no direct commit to main.

Protected finish line

If a test contradicts the confirmed Issue, stop for an owner-approved Goal Card revision. Never edit the card or weaken the test merely to obtain green output.

Compare the two handoffs

The harness changes.
The evidence boundary stays.

  • Local work exposes each decision.
  • Cloud work exposes delegation.
  • Both terminate in a PR.

  1. Open the local feature PR and record its head SHA, changed files, local evidence, and unresolved gaps.
  2. Return to the bug Issue. If Copilot finished, open its PR and verify that it copied the approved card, stayed inside the write boundary, and reported C01-C03. If it is still running, record IN PROGRESS and continue; do not manufacture completion.
  3. Compare the handoffs: which decisions were visible in the synchronous session, which were delegated, and which evidence must still be independently checked on GitHub?

Checkpoint: local DONE and cloud-agent completion are proposals tied to branch revisions. Neither is approval, merge authority, deployment evidence, or release authority.

Recovery and alternatives

A delayed agent
does not block learning.

  • Keep truthful session state.
  • Use references only for recovery.
  • Never invent a second PR.

The feature acceptance test does not fail
Compare it with the reference test. Confirm it runs against unchanged production code before using the reference implementation.
The skill is unavailable
Copy the matching reference Goal Card, bind its real Issue number, review every field, then publish it before execution.
Cloud assignment is unavailable
Keep the bug Issue unassigned and use the facilitator's source-bound cloud-agent example in Lab 3. Do not claim that a local fallback was Issue assignment.
The cloud agent is still running
Continue with the local feature PR. Revisit the session during Lab 3; its actual state is valid evidence.
A loop reaches a cap
Keep the branch or PR unmerged, record CAPPED and the failed checks, and use the matching reference artifact only to restore the workshop path.
