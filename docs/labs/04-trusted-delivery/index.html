Name exactly what can move

Reviewed head, merge SHA,
and artifact are different.

  • Review judges a PR head.
  • Merge creates a main revision.
  • Packaging creates identifiable bytes.

  1. Open the merged feature PR. Record the reviewed head SHA and the resulting merge commit SHA.
  2. Open the repository's Code page and confirm the merge commit is the current tip of main.
  3. Copy the full 40-character main SHA. This is the only candidate the prepared workflow accepts.

The workflow rejects an abbreviated SHA, a stale main revision, or a PR head that was never integrated. That prevents a green review from becoming an ambiguous release claim.

Checkpoint: you can state which revision was reviewed, which revision was merged, and which revision will be packaged.

Build deterministic evidence from that revision

The workflow accepts
one exact candidate.

  • Tests run at the candidate SHA.
  • Smoke checks exercise the service.
  • Packaging produces a digest.

  1. Open Actions, select Trusted release rehearsal, then choose Run workflow.
  2. Keep the workflow branch on main. Paste the full candidate SHA into Full main-branch commit SHA to package and promote.
  3. Start the run and open Build revision-bound evidence.
  4. Confirm the job validates candidate identity, checks out that exact SHA, requires it to equal current origin/main, runs npm test, and completes the three synthetic smoke checks.

Expected result: the package job is green and the promotion job waits for the workshop-preview environment reviewer.

Deterministic boundary

This workflow does not ask a model whether the release is good. It proves fixed conditions against fixed evidence and stops on failure.

A file name is not
artifact identity.

  • Digest identifies packaged bytes.
  • Manifest records producing context.
  • Smoke evidence names observed behavior.

  1. While promotion waits, open the package job summary and its uploaded release-candidate-<SHA> artifact.
  2. Confirm it contains pharmacy-reservation.tgz, pharmacy-reservation.tgz.sha256, and release.json.
  3. Read release.json. Match candidateSha, runId, repository, workflow, and the three smoke checks to the current run.
  4. Read the digest file. The SHA-256 value identifies the packaged bytes, not merely the source revision or artifact display name.

Checkpoint: you can move the artifact and its evidence together without losing the revision or producing workflow.

Keep evidence separate from authority

Green evidence informs.
The environment authorizes.

  • A reviewer reads exact evidence.
  • Approval resumes one environment job.
  • No production write occurs.

  1. Ask the configured reviewer to open the waiting deployment. The person who dispatched the run must not silently approve their own evidence.
  2. The reviewer verifies the candidate SHA, required job, artifact digest, smoke checks, and absence of unresolved release blockers.
  3. The reviewer approves workshop-preview. Open Promote approved workshop candidate and confirm it downloads the named artifact, verifies SHA-256, and checks release.json.
  4. Read the job summary. It must explicitly say that no external production deployment was performed.

The GitHub Environment creates a real deployment and approval record. In this workshop, "promotion" means verification at the preview boundary; it does not mean cloud resources or production changed.

Sandbox path

If required reviewers are unavailable, inspect the facilitator's source-bound recorded run, then execute the workflow only to observe packaging. Label environment approval unavailable; an immediate job is not equivalent to an enforced gate.

Make operational readiness explicit

Ready means traceable,
owned, and reversible.

  • Record evidence, not impressions.
  • Name rollback bytes and owner.
  • Missing authority means BLOCKED.

Add a comment to the merged feature PR using this structure:

Release rehearsal: READY | BLOCKED
Candidate SHA:
Workflow run:
Artifact SHA-256:
Smoke evidence:
Environment decision and approver:
Rollback artifact or prior known-good SHA:
Operational owner:
Unresolved blockers:

Use READY only when every field is concrete and the environment decision is recorded. Use BLOCKED when the merge did not complete, the candidate is stale, evidence failed, approval is unavailable, rollback is unknown, or ownership is missing.

Failure before packaging
Fix through a new PR. Never edit the generated evidence to make it green.
Rejected environment
Record the reviewer's reason and keep the candidate blocked.
Cloud deployment
Out of scope. A real implementation would add OIDC, a named target, health evidence, and rollback automation without weakening this boundary.
