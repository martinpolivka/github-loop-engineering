Connect your reviewed retail change to an approved, signed OCI image in Azure Container Registry.

Trusted delivery and operational readiness

Let your agent deploy the prepared test/prod resources into your allocated Azure group. Map two managed identities to GitHub Environments, then build once, sign in test, and approve promotion of the exact digest into prod.

Result: two tagged Azure environments, two distinct OIDC federations, and one image digest with separately verified test/prod signatures, a prod approval record, rollback candidate, and named owner.

Prepared start: the feature PR from Lab 3 is merged. The facilitator supplies your trusted resource-group allocation, Azure and GitHub access, prod reviewer, approved base-image digest, and working Azure CLI. The ARM resource template, /azure-release skill, Dockerfile, and .github/workflows/release-rehearsal.yml are already in your fork. You customize and deploy them; you do not write infrastructure from scratch.

This is the same retail API and storefront from Labs 1-3, with hardcoded synthetic stock and no database. ACR publication and signing are real Azure operations. Running the application in Azure Container Apps is optional; image security is the required outcome.

Workshop security model

Test and prod are tagged resources inside one allocated resource group, not separate groups. Both pipeline identities have Owner on that group by workshop design. Different tags and client IDs demonstrate mapping and GitHub approvals, not Azure authorization isolation or production least privilege. Never copy this shortcut into a production platform.

Own the allocation before deploying resources

One allocated group.
Two visible environments.

  • Your agent reviews a prepared IaC template.
  • Test and prod use different resources.
  • Owner is a workshop shortcut.

  1. Open the trusted allocation supplied by the lab platform. Confirm its subscription, existing resource group, and ownership tag. Never select an arbitrary group from a subscription list.
  2. Send: 
    /azure-release Prepare this fork in my allocated Azure resource group. Use the supplied allocation, review the prepared ARM template, guide me through naming and the prod reviewer, and deploy test/prod only after showing the plan and receiving my approval. Keep ACA off for the required path. Stop before wiring the GitHub federations.
  3. Review the proposed test/prod ACRs, vaults, identities, costs, and Owner-role shortcut. Approve the read-only Azure what-if first, then separately approve deployment. The template uses incremental group-scope deployment and cannot create a resource group.
  4. Watch the actual deployment complete. Inspect the resources and their Environment=test|prod and WorkshopStation tags. The allocator still owns cleanup of this group.

The template is ARM JSON deployed through Azure CLI: no Terraform provider install, remote state, or extra package setup is required. The agent may help customize parameters, but must not replace the reviewed template with invented infrastructure.

Checkpoint: your one allocated group contains separate test/prod resources. If deployment or role propagation hits the 15-minute cap, use the facilitator's prepared station and label the evidence accordingly.

Map identities before building once

Two identities.
Two environment subjects.

  • Test federation names workshop-test.
  • Prod federation names workshop-prod.
  • Environment variables select the correct client.

  1. Ask the same /azure-release agent to show both immutable GitHub environment subjects, Azure client IDs, issuer, audience, and expected variable scopes before writing the federations.
  2. Confirm that test maps to workshop-test and prod maps to workshop-prod, with different managed identities, ACR hosts, vaults, and public certificate fingerprints. Approve wiring only after checking your fork and allocation.
  3. Inspect both Environments in GitHub Settings. Each selects only main; prod also requires the chosen reviewer, blocks self-review, and disables administrator bypass.
  4. Inspect the ready workflow with your agent. Build has no Azure token; test uses the test environment; prod requires successful test and the separate approval. Each environment supplies a different AZURE_CLIENT_ID. Run the agent's read-back preflight.

Expected result: two real federated credentials and read-back-confirmed environment variables. OIDC uses short-lived tokens, never a client secret. Setup is not proof that an image has been signed.

A tag is a label.
A digest is identity.

  • Version tags make images findable.
  • Manifest digests name exact OCI bytes.
  • Source SHA and image digest differ.

  1. Record the feature PR head and merge SHA, then copy the current full 40-character main SHA. If the bug was also merged, the current tip includes both changes.
  2. Under Actions, run Trusted OCI release on main with that candidate SHA. The workflow rejects a stale SHA or a release started from another branch.
  3. Inspect Test and build exact retail revision: npm test, one image build from a pinned base, non-root container smoke checks, and no Azure credentials.
  4. Inspect Publish, sign, and verify in test. It loads the tested image without rebuilding, publishes a version tag to test ACR, signs the manifest digest through test Key Vault, and runs strict Notation verification.
  5. Read verified-test-<attempt>. Match source SHA, run/attempt, registry, manifest digest, smoke results, exact test signer, and public certificate fingerprint. Prod now waits for approval.

Checkpoint: source SHA, local image ID, mutable version tag, and OCI manifest digest are different. Signing always addresses registry/repository@sha256:....

Keep evidence separate from authority

Promote the digest.
Do not rebuild for prod.

  • A different reviewer approves the transition.
  • ORAS copies the identical OCI manifest.
  • Prod Key Vault supplies a different signature.

  1. Ask the configured reviewer to inspect the waiting workshop-prod deployment and test evidence. Self-review and administrator bypass are disabled.
  2. The reviewer checks the merged PR, SHA, strict test signature verification, image digest, rollback candidate, and unresolved blockers, then approves or rejects the transition.
  3. Open Promote exact test digest and verify the prod signature. The job uses the prod managed identity, rechecks current main and the test signature, and copies the manifest to prod ACR with ORAS.
  4. Confirm the target manifest digest is exactly the test digest. The prod vault signs with its own pinned key version; a new image build or a changed manifest fails the promotion.

Notation implements the Notary Project specifications. The workshop uses a non-exportable, self-signed test certificate with an explicitly approved trust root, not a public CA or production PKI. The signature authenticates a publisher of these bytes; it does not prove correctness or absence of vulnerabilities.

Expected result: one image digest in two registries, signed by two explicitly trusted environment publishers, with a real prod approval record. The tag prod means the workshop environment, not actual production infrastructure.

Make operational readiness explicit

Check both publishers.
Record a reversible decision.

  • Prod policy requires its own signer.
  • Rollback names another verified digest.
  • ACA is optional, not the finish line.

  1. Read verified-prod-<attempt> and the prod job summary. Confirm the test reference and prod reference have the same manifest digest.
  2. Inspect both trust policies: strict, exact registry repository, expected X.509 identity, and pinned public certificate fingerprint. Prod does not accept the test certificate as its publisher.
  3. Confirm prod notation verify succeeded. The signature authenticates the publisher of these bytes; it does not prove correctness or absence of vulnerabilities.
  4. Ask your agent to draft the release decision on the merged feature PR. Review the evidence and separately approve the GitHub write.

Use READY only when all fields are concrete. Identify a previously signed, verified image as the rollback candidate; if none exists in your new station, record BLOCKED rather than borrowing a digest from another repository. Missing approval, invalid signature, stale SHA, or missing owner also means BLOCKED. READY means a trusted release candidate, not proof of a production deployment.

Use the decision reference if you need recovery. It supplies the structure, not invented evidence.

Azure login or role failure
Ask the facilitator to repair the prepared station. Do not add passwords, registry admin access, or wider roles.
Stale candidate or failed signing
Record BLOCKED. Dispatch a new complete run for current main; do not rerun only failed jobs using an older attempt's artifact.
Failed signature verification
Keep BLOCKED. Never change strict to audit, trust arbitrary signers, or skip verification.
Sandbox or time limit
Read a facilitator-provided run with its original repository and SHA. Record this as recorded evidence, not a signed image from your fork. Missing capability in your fork remains BLOCKED.
Optional ACA
Enable ACA only after the image path is complete and time remains. The provided template and workflow run this same API plus same-origin frontend by verified digest, with zero-to-one ephemeral replica and no database. Stock resets on restart; an explicit ALLOWED_ORIGIN is available for a separate frontend, never wildcard credentialed CORS. Runtime identities get only AcrPull, not the Owner pipeline identity.
